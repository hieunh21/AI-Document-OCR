## 7. Duplicates and leakage control

| Item | Value |
|---|---|
| Duplicate groups (≥2 labelled images) | 37 |
| Labelled images inside such groups | 76 |
| Largest group | 4 |
| Linking pairs: identical bytes (SHA-256) | 55 |
| Linking pairs: near-duplicate photo (dHash) | 2 |
| Linking pairs: same transaction re-photographed | 4 |
| Labelled images that also appear in `val_images/` | 20 |

**dHash calibration.** A 64-bit dHash (8×8) is useless on this data: different receipts of the same chain collide at 1–2 bits because every photo is a white strip on a similar background. With a 1024-bit dHash (32×32), re-encoded/screenshotted copies of one photo were 78 and 110 bits apart, while the closest pair of *different* receipts from one store was 223 bits apart; the threshold is set to 150. Receipts photographed twice from a different angle are not caught by any global hash (≈500 bits apart) — they are caught by the transaction key (seller + timestamp to the minute + total), verified visually.

## 9. Implications for the next phases

- OCR/KIE must expect missing fields (~6–7% per field) and output `null`.
- `total_cost` extraction must pick the *amount* next to a total keyword, not the keyword and not item counts (`TẠI QUẦY 03`).
- Timestamp parsing must handle many separators (`/ - . :`), `CH/SA` (PM/AM), time-before-date, and check-in/out pairs.
- Report metrics on all images **and** on the clean subset; label noise caps EM.
- A few chains dominate: report per-stratum metrics so a rule tuned for VinCommerce does not hide failures on the long tail.
